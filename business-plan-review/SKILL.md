# Business Plan Review

gstack의 plan-ceo-review에서 문제 재정의, 대안 검토, 범위 유지·축소·선택적 확대를 가져왔다. 1인 사업의 검증 계획에 맞게 수정했으며 기술 설계 심사는 포함하지 않는다. [출처와 변경 범위](references/upstream.md)를 참조한다. 별도 런타임 없이 수행한다.

## 검토 기준 확정

대화와 계획에서 목적, 대상 고객, 기대 결과, 승인된 범위·비목표, 시간·현금 한도, 기존 검증 결과를 추출한다. 누락된 항목은 가정으로 표시하고 결론에 꼭 필요한 사용자 선택만 질문한다.

사업 방향·우선순위 또는 최신 상태에 의존하는 검토는 Notion의 Business HQ, About Business, Task Board와 관련 기록을 먼저 확인한다. 기록을 읽을 수 없으면 그 한계와 확인된 입력만으로 검토한다. 사용자가 제공한 일반적인 계획만 검토할 때는 불필요한 사업 현황 조회를 생략한다.

기본은 **범위 유지**다. 사용자가 최소 검증을 원하거나 운영 한도를 넘으면 **축소안**을, 사용자가 확대를 요청하거나 확인된 고객 병목 해소에 필요하면 **선택적 확대안**을 제안한다. 모드 선택을 위한 별도 승인 절차는 만들지 않는다. 추가·제외 항목은 사용자 결정 전까지 제안이며 승인된 필수 조건을 임의로 버리지 않는다.

## 검토

아래 관점 중 계획의 결론을 바꿀 항목을 검토한다. 각각 `계획의 주장 | 근거·출처 | 빠진 점 또는 반례 | 권장 수정 | 판단을 바꿀 검증`으로 정리한다. 사실, 사용자 진술, 가설, 추천을 분리한다. 점수 합계로 사업성을 판정하지 않는다.

| 관점 | 판단 질문 |
|---|---|
| 문제와 결과 | 어떤 고객이 어떤 상황에서 반복 손실을 겪는가? 제공할 결과가 그 손실을 줄이는가? |
| 수요와 대안 | 현재 대안을 버릴 이유와 전환 비용은 무엇인가? 관심·이용·결제 증거가 구분되어 있는가? |
| 획득과 메시지 | 고객이 이미 쓰는 표현과 유입 경로가 있는가? 발견→문의→구매 중 무엇이 미검증인가? |
| 지불과 경제성 | 이용자·비용 부담자·결제자가 누구인가? 가격 근거와 직접비, 고객당 작업 시간, 재작업·환불을 고려했는가? |
| 1인 운영 | 영업·납품·지원·품질 확인을 혼자 수행할 수 있는가? 수요 증가 시 가장 먼저 막힐 작업과 수용 한도는 무엇인가? |
| 범위와 검증 | 각 항목이 고객 결과 또는 핵심 전제 검증에 기여하는가? 더 싼 수작업·기존 도구·범위 축소로 같은 사실을 알 수 있는가? |
| 실패와 회수 | 검증 실패·납품 지연·품질 문제 때 고객에게 무엇을 알리고 어떻게 수습할 것인가? 중단 비용과 되돌릴 수 없는 약속은 무엇인가? |

인바운드를 먼저 검토하되 검색량을 구매 의사로 환산하지 않는다. SEO·콘텐츠는 고객 도달 경로, 수요 신호와 예상 학습 시간을 확인한다. 유입이 없으면 메시지·채널·노출 문제와 수요 부재를 분리한다. 콜드 아웃리치가 빠른 검증에 유리하면 대안으로 제안하되 실제 연락은 승인 범위 안에서만 한다.

계산에 쓸 수치가 있으면 단위와 기간을 맞춰 기여이익과 운영 시간을 계산하고, 사용자 노동시간의 단가를 명시한다. 수치가 없으면 변수 또는 범위로 두고 손익이나 처리 가능 고객 수를 사실처럼 말하지 않는다.

## 범위 제안과 완료

중요 발견부터 보고한다. 각 항목은 **유지 / 제외·연기 제안 / 추가 제안 / 근거 부족으로 미결정**으로 표시하고 이유와 시간·비용·운영 영향을 붙인다. 추천 변경과 사용자 승인 상태를 구분한다.

마지막에는 다음을 남긴다.

- 승인된 요구사항을 보존한 최소 실행안과 기존 계획에서 달라지는 부분.
- 가장 치명적인 미확인 전제, 이를 확인할 행동 하나와 관찰 지표·기간·비용 한도·성공 및 재검토 신호. 근거 없는 기준값은 제안으로 표시한다.
- 결론을 바꿀 반례와 남은 사용자 결정. 결론은 검증 진행·추가 조사·계획 수정·보류 중 **추천**으로 표현한다.

근거가 부족하면 business-research에 정확한 조사 질문을 넘기고 리뷰의 불확실성을 남긴다. 초기 문제 정의가 불명확하면 office-hours의 진단을 활용한다. 스킬 간 순차 실행은 의무가 아니다. 검토 요청만으로 제품 개발·공개·지출을 시작하거나 사업 상태·우선순위를 확정하지 않는다. 요청된 상세 검토는 기존 Notion 기록에 두고 로컬에는 링크와 요약만 남긴다.
